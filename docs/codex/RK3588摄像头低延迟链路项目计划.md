# RK3588 摄像头低延迟链路项目计划

## 1. 项目概述

本项目面向 RK3588 平台，目标是建立一条可复现、可测量、可演示的摄像头采集、图像处理、硬件编码和低延迟传输链路，并在主链路稳定后扩展 AI 感知、目标跟踪和云台/飞控联动能力。

核心技术链路：

`OV13850/MIPI -> CSI/DPHY -> CIF/ISP -> V4L2 -> RGA（按需） -> MPP -> RTP/RTSP -> PC 播放`

第一版基线：

- 输入：OV13850 MIPI CSI-2 摄像头。
- 图像输出：NV12。
- 视频规格：1080p30。
- 编码格式：H.264，后续扩展 H.265。
- 传输方式：RTP/RTSP。
- 优化方向：低拷贝、低延迟、稳定运行、故障可定位。

## 2. 项目原则

- 本项目是用户的学习项目，用户负责主要动手实践，Codex 负责讲解、拆解、示范、评审和陪同调试。
- 默认按“原理讲解 -> 小任务拆分 -> 用户实现 -> 结果检查 -> 调试引导 -> 复盘总结”推进。
- 未经用户明确授权，Codex 不得一次性完成整个阶段、完整功能或大批量代码修改。
- 代码修改前应先说明目标、涉及文件和学习重点，由用户决定亲自实现还是授权 Codex 修改。
- 只有用户明确要求直接实现时，Codex 才代为编码，并继续保持小步说明和验证。
- 先保证每一层功能正确，再进行跨层性能优化。
- 每一阶段都必须有日志、命令、数据或输出文件作为验证证据。
- RGA 仅在需要缩放、旋转或格式转换时使用，不作为固定必经节点。
- 正式 `ov13850.c` 作为主要学习和交付驱动，`ov13850_i2c_min.c` 仅用于寄存器验证和故障定位。
- AI 推理作为独立分支，不能阻塞摄像头采集、编码和推流主链路。

## 4. 阶段 0：基线验证（已完成）

### 目标

确认摄像头能够被系统正确发现，Media Controller 拓扑完整，并能从正确的视频节点稳定采集图像。

### 主要内容

- 通过 `dmesg` 确认 OV13850 probe 状态。
- 使用 `media-ctl -p` 查看 Sensor、DPHY、CSI/CIF、ISP 和 Video Node 的连接关系。
- 使用 `v4l2-ctl` 采集图像或视频帧。
- 确认像素格式、分辨率和实际帧率。

### 完成标准

- 摄像头能够正常 probe。
- 媒体拓扑不存在断链或错误 endpoint。
- 能从正确的 `/dev/video*` 节点稳定采集图像。
- 能解释从 Sensor 到 Video Node 的完整数据路径。

## 5. 阶段 1：传感器与 DTS（已完成）

### 目标

掌握 OV13850 的硬件资源配置，以及设备树节点到驱动 `probe` 的匹配过程。

### 主要内容

- 梳理供电、外部时钟、复位 GPIO 和 PWDN GPIO。
- 确认 I2C 地址、MIPI Lane 数量和 link frequency。
- 理解 Sensor、DPHY、CSI/CIF、ISP 之间的 endpoint 连接。
- 掌握 Camera DTS、DTSI 和 DTBO overlay 的关系。
- 跟踪 `compatible -> of_device_id -> probe` 匹配过程。

### 完成标准

- 能独立解释并修改 Sensor 到 ISP 的设备树链路。
- 能根据启动日志定位供电、时钟、I2C、MIPI 和 endpoint 问题。
- 能确认设备树修改最终进入实际加载的 DTB/DTBO。

## 6. 阶段 2：V4L2 驱动完善（当前阶段）

### 目标

以正式 `ov13850.c` 为主线，掌握完整 V4L2 Sensor Subdev 驱动，并完成一次具有明确需求和测试证据的驱动改动。

### 主要内容

- 梳理 `probe`、上电、下电、runtime PM 和 `remove` 流程。
- 梳理 `stream on/off`、模式选择和寄存器表写入过程。
- 核对 mode table 中的分辨率、HTS、VTS、FPS、link frequency 和 pixel rate。
- 验证曝光、模拟增益、VBLANK 和测试图等 V4L2 Controls。
- 检查控制值变化是否正确转换为 Sensor 寄存器值。
- 完成一次驱动改动，例如增加模式、修正控制范围或补充错误处理。
- 使用 `v4l2-compliance`、连续启停和持续采集验证驱动行为。

### 完成标准

- 能解释关键驱动调用链和模式参数之间的计算关系。
- 驱动改动具有明确需求、代码变更、测试命令、日志和采集结果。
- 连续 stream on/off 不出现资源泄漏、I2C 错误或无法恢复的问题。
- 持续采集过程中没有明显丢帧、花屏或 MIPI 错误。

## 7. 阶段 3：ISP 与 RGA 图像处理

### 目标

理解 RAW 图像经过 RKISP 输出 NV12/YUV 的过程，并按实际需要使用 RGA 完成硬件图像处理。

### 主要内容

- 区分 CIF 旁路、ISP 主路径和自路径视频节点。
- 确认 Sensor Bayer 格式、ISP 输入格式和输出格式。
- 将 ISP 输出固定为适合 MPP 输入的 NV12。
- 编写 V4L2 取帧程序，明确缓冲区申请、入队、出队和回收过程。
- 使用 RGA 完成缩放、旋转和色彩空间转换。
- 对比 CPU 处理和 RGA 处理的资源占用与吞吐。
- 不需要图像变换时绕过 RGA，减少额外排队和处理延迟。

### 完成标准

- 能稳定输出指定分辨率和帧率的 NV12 数据。
- RGA 输出尺寸、stride 和像素格式正确。
- 能说明启用或绕过 RGA 对延迟、CPU 占用和内存带宽的影响。

## 8. 阶段 4：MPP 硬件编码

### 目标

将摄像头输出交给 RK MPP，生成可稳定解码的 H.264/H.265 硬件编码码流。

### 主要内容

- 跑通 NV12 到 MPP Encoder 的最小编码程序。
- 配置分辨率、帧率、码率、GOP、编码格式和码率控制模式。
- 支持 IDR 帧和关键帧请求。
- 先完成普通内存输入版本，再切换到 DMA-BUF/DRM Buffer 低拷贝路径。
- 明确 V4L2、RGA 和 MPP 之间的缓冲区所有权及生命周期。
- 检查码流时间戳、帧顺序、SPS/PPS 和编码错误恢复。

### 完成标准

- 能持续生成可正常解码的 1080p30 H.264/H.265 码流。
- 码流帧率、码率和 GOP 与配置一致。
- 能明确整条编码路径的数据拷贝次数和缓冲区流向。

## 9. 阶段 5：低延迟视频流

### 目标

通过 RTP/RTSP 将硬件编码码流发送到 PC，并控制采集、编码、网络和播放端的累计延迟。

### 主要内容

- 使用 GStreamer 验证 RTP/RTSP 发送和 PC 端接收。
- 调整 GOP、B 帧、码率控制、关键帧间隔和编码缓存。
- 缩短采集、编码、发送和播放队列。
- 调整接收端 jitter buffer、播放器缓存和丢帧策略。
- 正确处理 PTS、DTS 和 RTP 时间戳。
- 实现断开重连和关键帧恢复。
- 为采集、ISP、MPP、网络发送和显示环节记录时间戳。

### 完成标准

- PC 端能够稳定播放视频。
- 端到端延迟可以重复测量，并能分解主要延迟来源。
- 网络短暂断开后，视频链路能够自动恢复。
- 队列积压时能够主动丢弃旧帧，避免延迟持续累积。

## 10. 阶段 6：性能测量与稳定性

### 目标

使链路行为可解释、性能可复现，并形成能够指导后续优化的测量结果。

### 主要内容

- 测量端到端延迟、FPS、丢帧率和实际码率。
- 记录 CPU、内存、DDR 带宽和芯片温度。
- 对比普通内存拷贝路径和 DMA-BUF 低拷贝路径。
- 对比启用 RGA 与绕过 RGA 的性能差异。
- 执行持续推流、反复启停、网络抖动和异常断开测试。
- 整理 Sensor、ISP、RGA、MPP 和网络各层的故障定位方法。

### 完成标准

- 形成可复现的性能测试命令和结果数据。
- 能指出当前主要延迟来源、带宽瓶颈和资源消耗点。
- 长时间运行过程中不存在不可恢复的断流、资源泄漏或温度失控问题。
- 常见异常具备日志证据和分层排查步骤。

## 11. 阶段 7：AI 感知与业务扩展（可选）

### 目标

在稳定视频链路上增加 RKNPU 推理、目标跟踪、OSD 以及云台/飞控联动能力，同时保证主视频链路不被阻塞。

### 主要内容

- 从视频链路分支出独立的 AI 输入队列。
- 使用 RGA 完成 resize、颜色转换等模型前处理。
- 使用 RKNPU 执行目标检测或跟踪模型。
- 将推理结果绘制为 OSD，或输出给云台和飞控模块。
- 设置有界队列和丢帧机制，避免 AI 处理速度影响主链路。
- 测量 AI 开启后的推理帧率、新增延迟和资源占用。

### 完成标准

- AI 模块关闭或异常时不影响采集、编码和推流。
- 推理结果具备明确坐标、时间戳和来源帧关联关系。
- 能量化推理帧率、处理延迟和系统资源占用。

阶段 2 的首要任务是梳理正式 `ov13850.c` 的以下调用链：

1. `probe -> 资源获取 -> control 初始化 -> subdev 注册`。
2. `runtime_resume -> power_on -> 寄存器访问`。
3. `set_fmt -> mode 选择 -> control 范围更新`。
4. `s_stream -> mode table 写入 -> control setup -> stream on`。
5. `stream off -> runtime_suspend -> power_off`。

完成调用链和参数关系梳理后，再选择一个能够在实机验证的驱动改动作为阶段 2 的交付任务。
